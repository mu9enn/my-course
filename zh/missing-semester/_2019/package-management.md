软件通常会基于（一个或多个）其他软件来构建，这就不可避免地需要依赖管理。

包管理 / 依赖管理工具因编程语言而异，但许多核心概念在不同语言之间是通用的。

# 包仓库

软件包托管在 _包仓库_（package repository）中。不同语言有各自的包仓库（有时某一语言还有多个仓库并存），例如 Python 的 [PyPI](https://pypi.org/)、Ruby 的 [RubyGems](https://rubygems.org/)，以及 Rust 的 [crates.io](https://crates.io/)。这些仓库通常会保存一个软件包的**所有版本**——包括源码，有时也包括针对不同平台预编译好的二进制文件。

# 语义化版本

软件会随时间演进，我们需要一种方式来引用特定的版本。最朴素的方法是用序列号或者 Git 的 commit hash 来标识，但我们可以通过版本号来传递更多有用的信息。

业界有多种版本编号方案，其中一种广为人知的是 [语义化版本](https://semver.org/)（Semantic Versioning）：

```
x.y.z
^ ^ ^
| | +- patch
| +--- minor
+----- major
```

- 当你做出 **不兼容** 旧版本 API 的变更时，增加 **major（主版本号）**。
- 当你以**向后兼容**的方式添加新功能时，增加 **minor（次版本号）**。
- 当你以**向后兼容**的方式修复 Bug 时，增加 **patch（修订号）**。

例如，如果你的项目依赖某个软件在 `v1.2.0` 中引入的一项功能，那么你可以安装 `v1.x.y`，其中次版本号 `x >= 2`、修订号 `y` 取任意值。你必须锁定主版本为 `1`（因为主版本 `2` 可能引入向后不兼容的变更），同时次版本号必须 `>= 2`（因为你依赖的功能正是在这个次版本中引入的）。在修订号和更新的次版本之间，你可以选用任何更新的版本，因为它们不应引入向后不兼容的变更。

# 锁文件

除了声明版本号之外，有时我们还需要确保依赖的**内容**没有发生过改动——以防有人往仓库里投放被篡改过的包。部分工具会使用 _锁文件_（lock file）来记录每个依赖的**加密哈希值**（连同版本号一起），在安装包时进行校验。

# 指定版本

包管理工具通常允许你用多种方式声明版本要求，常见的有：

- **精确版本**，例如 `2.3.12`
- **最低主版本**，例如 `>= 2`
- **指定主版本 + 最低修订版本**，例如 `>= 2.3, <3.0`

**精确版本**的优点是避免不同环境中因依赖版本不同而产生差异行为（如果所有依赖都严格遵循语义化版本，这种情况本不该出现——但现实中总有人犯错）。**最低版本要求**的优点则是允许自动安装 Bug 修复（即修订号升级）。

> **译者注：** 这里原文将第三种方式称作“最低修订版本”，但示例 `>= 2.3, <3.0` 实际限制的是下界和主版本上界，仍允许后续的 `2.x` 次版本，并非只允许修订号变化。理解版本范围时，应以表达式本身为准。

# 依赖解析

包管理器使用各种依赖解析算法来满足你的依赖声明。当依赖关系变得复杂时，这事往往会变得棘手——例如，一个包可能被多个顶级依赖间接依赖，而不同顶级依赖又要求该包的不同版本。不同的包管理器在依赖解析上的精细程度各不相同，但这一点你应当有所察觉：如果你需要排查依赖冲突，理解这些算法的基本原理会很有帮助。

# 虚拟环境

如果你在同时开发多个软件项目，它们可能会依赖同一个软件的**不同版本**。有些构建工具会自然地处理好这个问题（例如通过编译为静态二进制文件，把所有依赖"打包"进最终产物中）。

对于其他构建工具和编程语言，一种常用思路是使用 _虚拟环境_（virtual environment）。以 Python 为例，[virtualenv](https://docs.python-guide.org/dev/virtualenvs/) 就是经典代表。与其将依赖安装到系统全局范围，不如在每个项目中安装独立的依赖，并在你切换到某个特定项目时 **激活**（activate）对应的虚拟环境。

# 依赖内嵌（Vendoring）

依赖管理的另一种完全不同的思路是 _依赖内嵌_（vendoring）。你不再依赖包管理器或构建工具从仓库拉取软件，而是将某个依赖的**完整源码**直接拷贝到你自己的仓库中。

这样做的优势在于：你永远是在同一个确切版本上构建，且不需要依赖外部包仓库。代价则是升级依赖的成本更高——每次都需要手动拉取、审查并替换源码。
