# 实践问题

本附录涵盖规模化运行后训练实验时的各项实际考量。内容以经验清单的形式呈现，而非连贯的叙述性章节。

## 后训练的算力成本

衡量后训练实验的成本有两种不同的视角。最大的成本在于"开发配方"——为某个后训练方案摸索出一套可用的超参数组合——这部分往往消耗最终正式训练算力的 10 到 100 倍。次要成本则更容易量化，指的是"完整应用一套配方"所需的开销：运行多个随机种子、进行细致的评估、处理工程上的麻烦事，等等。

关于第一种成本（开发配方），以 Tülu 3 [@lambert2024t] 的后训练配方开发为例，团队在产出最终模型之前，在 7B 规模上进行了数千次实验和评估。

关于第二种成本（完整应用配方），Olmo 3 报告详细记录了训练最终 32B Think 模型所涉及的工作量 [@teamolmo2025olmo3]：

> 后训练采用的运行模式有所不同：每个阶段都会多次运行，在学习率和其他超参数上进行搜索扫描。后训练（尤其是强化学习）的理论基础还不够成熟，因此必须运行多个实验才能为给定基座模型找到最优超参数。我们希望未来工作能弥补这一不足。
>
> 在后训练阶段，检查点评估消耗了更大比例的算力资源，部分原因是推理模型的长文本生成消耗了核心基准测试的大量计算。对于监督微调（SFT），我们在 256 张 GPU 上以并行方式扫描了四个候选学习率，每个持续 36 小时；随后约 12 小时用于评估、合并和检查点确认，总计约两天。DPO 训练的单次运行时间较短（在 64 张 GPU 上完成完整学习率扫描约 18 小时），但由于集群不稳定，实践中跨越了数天。最初的 Olmo 3 Think 32B 的最终强化学习运行约持续了 5 天，其中因稳定性问题至少损失了一天训练时间。Olmo 3 首次发布之后，我们在 224 张 GPU 上继续运行表现最好的那次强化学习训练，历时 21 天，最终产出了 Olmo 3.1 Think 32B。

随着强化学习规模化成为更常规的做法，情况还将继续变化 [@khatri2025art]。以上述例子继续说明：原始的 Olmo 3 32B Think 后训练仅耗时两周左右，而要发布改进版 Olmo 3.1 32B Think，团队又使用 RLVR 额外训练了 3.5 周。这里更大的成本在于时间，而非总算力。

## 评估方差

后训练中一个常被低估的挑战是评估方差，尤其是随着需要使用采样温度大于 0 的推理模型来提高评估分数的普及，这个问题更加突出。任何涉及从模型进行采样的场景中，输出都会变得更加不稳定。不同的基准测试在稳定性上差异巨大，原因包括提示词难度本身的波动、评估集中的提示词数量、被训练模型的脆弱性，等等。

在 Olmo 3 项目期间，团队跟踪了用于评估推理模型的不同基准的方差。下表展示了各基准评估的标准差，计算方式为：对 14 个模型各运行 3 次，取每次评估的标准差均值（先计算每个模型各自的方差，再按评估指标求平均）：

| 类别 | 基准测试 | 标准差 |
|----------|-----------|-----------|
| 高方差 | GPQA | 1.48 |
| | AlpacaEval 3 | 1.24 |
| | IFEval | 0.88 |
| 稳定 | ZebraLogic | 0.56 |
| | Omega | 0.56 |
| | AIME 24 (Avg@32) | 0.54 |
| | HumanEvalPlus | 0.46 |
| | AgiEval | 0.43 |
| | BigBenchHard | 0.39 |
| 非常稳定 | LiveCodeBench (Avg@10) | 0.29 |
| | MBPPPlus | 0.27 |
| | MATH | 0.25 |
| | MMLU | 0.22 |
| | PopQA | 0.16 |

有些评估（例如 LiveCodeBench）既噪声较大又便宜（评估集中的提示词数量少），因此通过对每个模型重复运行 10 次评估，可以将该评估从"高方差"类别移到"稳定"类别。理论上可以对所有评估都这样做，但这很容易导致成本大幅膨胀。

此外，评估设置中的批大小、vLLM 内的张量并行配置（例如基线模型使用 TP=2），以及其他涉及长文本生成的基础设施敏感数值，都会引入方差。在推理模型的评估中，方差无处不在。

## 训练性能方差的管理

本书讨论的所有后训练配方和工具中，最终模型的性能始终存在显著的方差。理解这一方差的分布、来源及其影响，对于打造高质量模型至关重要。训练最终模型的目标是通过调整训练参数和随机种子，采样尽可能多的结果点，以找到最强的模型。需要注意的是，这里的关键在于模型是否*真正*变得更好，而不只是通过重新采样（re-roll）碰巧避开了评估噪声。

上一节聚焦的是*评估*噪声，而更为棘手的噪声来源是*训练不确定性*。评估噪声可以通过对同一检查点进行更多测试来管理（均匀地降低噪声），但模型只训练一次，并且有可能因正离群值而*受益*——即恰好遇到了一次效果超出均值的训练。

实践中，训练团队会采取多种手段来尽可能榨取训练配方的全部价值：

1. 对每次最终训练运行，搜索核心优化值，如学习率、批大小等。例如，使用新基座模型时，建议先在较宽的学习率范围内运行 10 个学习率，确保处于最优区间，然后在更窄的最优窗口内重新运行。
2. 对最佳少数超参数设置，使用多个随机种子运行。随机种子可能对最终模型产生明显影响，值得投入算力。
3. 模型合并（Model Merging）已被确立为打造强模型的关键工具。合并可以通过多种方式进行，从合并相同数据上的不同检查点，到合并针对特定领域训练的专业模型。总体而言，合并是最终配方中强大且简单的工具，但针对如何在配方中为后续合并准备模型，尚未形成明确的 best practices [@yadav2024matters]。

## 识别有问题的训练任务

一个在训练模型时需要建立的重要直觉是区分不同类型的模型问题。你应当把大部分时间花在"当前数据、算法或配方不够好"的问题上。另一方面，也有大量情况是：在开发新配方时，某些方法本身就已经行不通了。

理解这一点最好的方式是使用基本不变的评估套件，对大量模型进行评估。然后你就会对哪些测试在经过去训练干预后难以取得进步形成直觉（通常是知识密集的评估，如 MMLU）。当后训练设置中存在严重问题时，这些高度稳定的评估指标往往会在单次训练任务中下降 10 到 20 个百分点。这是开发调试工具时最有用的信号之一！
